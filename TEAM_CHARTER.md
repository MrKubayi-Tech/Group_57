### Project Overview

The Northstar Retail Co. Support Deflection MVP is a backend automation system designed to process incoming customer support tickets and automatically resolve or tag routine inquiries before they reach a support agent.

The MVP focuses on two primary ticket categories:

1. **Order Status**
2. **Stock Availability**

The system will process incoming ticket information, check relevant company data, provide automated responses or tags for routine inquiries, and escalate unknown or unsupported requests to human support agents.

# 5. Task Assignment and Time Management

All project tasks will be tracked using the team's Jira project board.

## Task Assignment

- Tasks must be assigned to a specific team member.
- Assigned tasks must be accepted within **24 hours**.
- Each task must have a clear description.
- Each task must have a priority.
- Each task must have a Definition of Done.
- Each task must have an estimated completion time.

## Internal Deadlines

Draft deliverables should be completed **at least two days before the official project submission deadline** to allow sufficient time for:

- Team review.
- Testing.
- Integration.
- Bug fixing.
- Documentation.
- Final submission preparation.

## Late Tasks

If a member expects to miss an agreed deadline, they should notify the team at least **24 hours in advance** whenever reasonably possible.

The member should communicate:

1. The affected task.
2. The reason for the delay.
3. The expected completion date.
4. Whether assistance from another team member is required.

# 7. Anti-Black-Box Rule

No individual project task may exceed **4 hours**.

If a task is expected to take more than four hours, it must be broken down into smaller, independently verifiable tasks.

This ensures that project work remains:

- Granular.
- Measurable.
- Assignable.
- Trackable.
- Independently verifiable.

The team's Assignment 1 project board contains tasks that comply with the maximum four-hour requirement.

---

# 8. Definition of Done

Each Jira task must have a clear Definition of Done.

A task may only be moved to **Done** when its stated Definition of Done has been satisfied.

Where applicable, completion should also include:

- Successful testing.
- Code review.
- GitHub commit.
- Documentation updates.
- Successful integration with related components.

# 9. Decision-Making Rules for Disagreements

The team will use the following process when disagreements occur.

### Step 1 – Direct Discussion

Members involved in a disagreement should first discuss the issue respectfully and explain the reasoning behind their positions.

### Step 2 – Team Consensus

The team will attempt to reach a solution that all members can reasonably accept.

### Step 3 – Majority Vote

If consensus cannot be reached, the team will use a simple majority vote.

Each team member has one vote.

### Step 4 – Admin / Team Lead

If the vote results in a tie or the disagreement continues to prevent project progress, the Admin will coordinate a further discussion and recommend a practical resolution.

### Step 5 – Course Facilitator

If the dispute remains unresolved or significantly affects project completion, it will be escalated to the course facilitator.

---

# 10. Conflict Escalation Path

The agreed escalation path is:

```text
Trigger
   ↓
Direct Discussion
   ↓
Full Team Discussion
   ↓
Majority Vote
   ↓
Admin / Team Lead
   ↓
Course Facilitator
```

### Conflict Triggers
The escalation process may be initiated when:
* A technical disagreement cannot be resolved.
* A member repeatedly misses assigned deadlines or fails to communicate.
* A member repeatedly fails to complete assigned work.
* A disagreement significantly affects project progress.
* A team member's work prevents another member from completing their assigned task.

## 11. Branch and Naming Convention

The team will use Git branches to separate development work following standard conventions.

**Pattern:** `<type>/<short-description>`

### Approved Types
* `feature/`
* `fix/`
* `docs/`
* `refactor/`
* `test/`

### Branch Examples
* `feature/ticket-parser`
* `feature/order-status-lookup`
* `feature/stock-availability`
* `feature/ticket-dashboard`
* `fix/ticket-validation`
* `docs/project-documentation`
* `test/order-status`

---

## 12. Commit Naming Convention

All commits should follow the standard format:

`<type>: <what changed> - <why it matters>`

### Commit Examples
* `feat: add order status lookup - automate routine status requests`
* `fix: validate order IDs - prevent invalid lookup requests`
* `test: add stock lookup tests - verify inventory edge cases`
* `docs: update setup guide - simplify project installation`
* `refactor: reorganize ticket parser - improve maintainability`

---

## 13. Pull Request and Code Review Rules

Development work must be submitted through a GitHub Pull Request before being merged into the main branch:

```text
Create Branch → Develop → Commit Changes → Push Branch → Create Pull Request → Code Review → Address Feedback → Merge
```
*The team should avoid directly committing unreviewed development work to the protected main branch.*

---

## 14. Main and Development Branches

* **`main`:** Contains stable code suitable for demonstration or submission.
* **`dev`:** Used for integrating completed development work before final release.

Feature and fix branches should be created from the appropriate development branch and merged through the agreed review process.
